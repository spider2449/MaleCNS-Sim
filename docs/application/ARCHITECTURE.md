# Visual experiment workbench: A001 architecture contract

Status: A001 design, 2026-10-01. Decision: **APP1 — ARCHITECTURE_READY_FOR_IMPLEMENTATION**. Engine boundary: **E2 — THIN_APPLICATION_ADAPTER_REQUIRED**. This document specifies new application experiments; it does not revise historical Tasks 010, 011, 017, or 018. The workbench exposes connectome data, declared model assumptions, actual simulation output, and provenance. It is not a second simulator.

## A002 implementation note (2026-10-01)

`malecns_sim.application` now implements the A001 v1 experiment/result contracts, a bounded CPU/CUDA service, explicit lifecycle events, atomic JSON result interchange, and a synthetic engine integration test. The implementation record and exact limits are in [the A002 plan](../plans/2026-10-01-application-a002-service-contracts.md). The signed projection returned by `prepare_network` uses the reference 0.275 mV anatomical-synapse factor, so A002 rejects other projection weights before execution and verifies the sign/resolution IDs against the prepared projection. A002 computes run identity from the validated curated unsigned graph fingerprint declared in the spec; preparation verifies that fingerprint and records the actual effective projection fingerprint in result provenance. This makes `RunStarted` and every subsequent event share one stable run ID. A003 must supply registered dataset files and own the local API/session security boundary.

## A003 local shell (2026-10-01)

Launch from the repository root with `uv run malecns-workbench`. The launcher binds `127.0.0.1:8765` and prints the local URL containing a per-process token in the URL fragment. `--port 0` requests a free local port. An occupied fixed port fails rather than switching silently. The registered dataset root defaults to `./data`; `MALECNS_DATA_ROOT` can select a trusted local data root for an installed package. The browser sends only the allowlisted dataset key, side, frequency, mode, backend, and seed. The server registers exact MaleCNS v1.0 filenames and pinned identities and constructs the A002 `ExperimentSpec`. Missing files yield `DATASET_UNAVAILABLE` while the UI remains available.

The stdlib `ThreadingHTTPServer` serves packaged HTML, CSS, and JavaScript. It accepts only exact loopback Host, checks Origin, and requires the per-process token and same Origin on POST. JSON input has a 2 KB body cap and exact selection fields; A002 validates the constructed spec and executes via `run_experiment`. There is no path, shell, Python module, historical runner, or arbitrary file API. One daemon worker may run at a time; eight recent runs are retained in memory. Events are polled once per second from A002 event envelopes. The result export is the checked A002 JSON manifest written inside the server-controlled temporary root. No data persists across server restart.

The layout has setup on the left, logical data flow and result in the center, run inspector on the right, and actual event history below. It has no anatomy coordinates, synthetic progress percentage, or activity animation. A004 remains responsible for a bounded graph renderer and neuron inspector. See [the A003 plan](../plans/2026-10-01-application-a003-local-visual-workbench.md) for certification and measurements.

The CPU and CUDA engines label spikes with `step + 1` during `range(duration_ms / dt_ms)`. For an exact grid of `N` updates, legal spike timesteps are the integers `1..N`, including the terminal timestep `N`; zero, negatives, nonintegers and values above `N` are invalid. The service checks the engine's integer arrays before conversion. The bounded browser selection receives a deterministic experiment UUID, so Validate and Run construct identical canonical `ExperimentSpec` bytes and digests. Each execution retains a separate invocation/job identity.

## ExperimentSpec v1

Serializable canonical JSON with strict unknown-field rejection; finite JSON numbers only; explicit units. Required fields: `experiment_schema_version="application-experiment-v1"`, `experiment_id` (user or generated stable UUID, never a historic Task ID), `dataset` (release, manifest digest, source file SHA-256, curated projection fingerprint, annotation/mapping fingerprint), `backend` (`cpu_reference` or `cuda`), `seed_policy` (`explicit` with per-trial integer seeds, or a documented deterministic derivation), `duration_ms`, `dt_ms`, `trial_count`, `stimulus` (frozen sugar population fingerprint, actual member IDs, `rootSide` L/R, frequency Hz, start/end ms, Poisson weight factor and input semantics), `target` (MN9_L=10331 or MN9_R=16949 and side relation), `intervention` (`none` or `outgoing_silence`, exact validated target IDs), `model` (all LIF parameter values and fingerprint), `sign_policy` (policy and resolution IDs), `observables` (spikes, selected trace IDs, optional delivery trace and requested bins), and `robustness` (`none` or explicit variant set, independent seeds/parameter differences and optional backend rule ID). The first UI offers a bounded allowlist of frequencies and one silencing target from a documented candidate set; A002 must choose and test the precise limits. Validation checks that population and intervention IDs exist in the curated graph, stimulus timing aligns to dt, probability `rate_hz * dt_ms / 1000 <= 1`, trace count and duration respect resource limits, and requested backend is available. An application spec may reference historical identity evidence but cannot mutate a historical Task artifact or claim to rerun its preregistration.

Canonical spec digest: SHA-256 of UTF-8 canonical JSON (sorted keys, compact separators, normalized finite numeric representation, no paths that vary by machine). Define canonicalization precisely in A002 and test equivalent serialization. Scientific execution identity binds spec digest, dataset/file and graph fingerprints, engine package version, LIF and sign policy fingerprints, explicit realized schedule fingerprint, seed(s), backend, and result schema version. `run_id` is a digest of that identity with domain prefix, so exact repeats share an execution identity; a separate invocation ID distinguishes repeats. Timestamp, duration, host, hardware, and Git commit are metadata. Record Git commit and dirty state when available; installed packages without `.git` remain valid using package version and installed distribution/build provenance. Distinguish an uncommitted local engine from a clean reproducible build in provenance. Result identity also binds authoritative data hashes.

## Execution and event contract

State order: `CREATED → VALIDATING → LOADING_DATA → PREPARING_NETWORK → RUNNING → FINALIZING → COMPLETED`. `FAILED` and `CANCELLED` are terminal from any active phase, with phase, structured reason and last completed trial. CUDA initialization is a labeled activity within preparation; result serialization is a labeled activity within finalization. Robustness variants use `RUNNING` with `variant_id`, completed/total *trials* or *batches*. No generic percentage for graph loading or a single opaque CPU/GPU simulation. Cancellation is cooperative between trials or before/after a single engine call; a running single trial cannot promise immediate cancellation.

Every event has `event_schema_version`, `run_id`, invocation ID, monotonic sequence, wall-clock timestamp, phase, and payload. Persist lifecycle events (`RunStarted`, `PhaseChanged`, `TrialStarted`, `TrialCompleted`, `RunCompleted`, `RunFailed`, `RunCancelled`) in order, immediately at transitions, including actual trial/variant identifiers, backend and result/digest or error. `TrialCompleted` follows committed authoritative trial data. Optional throttled `SpikeBatch`, `PopulationActivitySample`, `TraceSample`, and `SimulationTimeAdvanced` are visualization-only, ordered within a trial, may be dropped under backpressure, and never enter scientific digests. Existing engines emit no in-loop events, so A003 can create these only from completed result data and label them replay/preview, not live simulation time. Phase events and completed trial counts are true live progress. The UI must not infer scientific evidence from frame delivery.

## ExperimentResult v1 and playback

Result manifest fields: `result_schema_version="application-result-v1"`, run/spec digests and full executed spec, status, invocation timestamps/timings, backend, dataset/engine/Git provenance, resolved stimulus schedule summary/fingerprint, resolved intervention IDs/semantics, graph/model/sign fingerprints, per-trial seeds, target spike counts/rates, response time series, sparse spike-data reference and engine digest, selected-neuron v/g trace reference, population summaries, optional comparison and robustness records, warnings, file SHA-256 and manifest integrity digest. Authoritative numeric data are engine-produced spikes (`int64` IDs/timesteps), counts, selected traces and fingerprints plus backend-derived summaries with declared algorithms. Visualization bins/layout coordinates/colors are derived, labeled with source digest and binning version; they can be regenerated and never override numeric evidence. Use atomic artifact writes and validate hashes on read/export. Failed/cancelled partials have explicit status and completed-trial listing, no implied full result.

First playback representation: **hybrid** sparse canonical spike events + optional bounded selected-neuron traces + derived binned population counts. Timeline is `[0,duration_ms]`, discrete dt; scrubbing queries event ranges, stimulus schedule active interval/events, target spikes/rate bins, and intervention active interval. A run with S spikes needs `16*S` bytes for two int64 spike arrays before container/compression/index overhead. At 1 ms bins over 1 s, one float32/count series uses 4 KB per population; 16 selected neurons with both v/g float64 traces at 0.1 ms use about 2.56 MB. Full v/g traces for 127,400 neurons over 10,001 samples would use about 20.4 GB, so they are excluded. Actual spike counts, compression ratio, playback memory and artifact size are `MEASUREMENT_REQUIRED`; enforce A002 configurable result size/trace caps before run.

## Network and spatial view

The **127,400 neurons / 14,687,178 edges** counts are authoritative for the original Shiu v630 completeness/connectivity inputs (`data.shiu_v630.ShiuV630Reference`, Task 006); they must not be labeled as the curated MaleCNS v1 simulation graph. The application records and displays actual curated projection node/edge counts at preparation. Never send/render the full graph as DOM/SVG. Level 0: population/stimulus/target overview. Level 1: bounded directed signed subgraph. Level 2: selected neuron IDs, annotations and exact edge direction/weight/sign policy. Future Level 3: separately sourced morphology with coordinate provenance and alignment. First-slice extractor takes graph fingerprint, seed set (frozen sugar population, MN9, explicit user IDs, optional candidate IDs), max hops, edge direction, edge-weight ranking, node/edge caps, and deterministic tie-break by IDs. It returns exact included IDs/edges, truncation counts, filter parameters and a warning that selection is a display filter, not a discovered biological pathway. A002 sets concrete caps after measurement.

Spatial classification: **V5 — MIXED**. Local MaleCNS annotation data include `somaLocation`/`tosomaLocation` and side/neuromere metadata for some neurons (`analysis.task008a`), with missing values and coordinate-frame questions. Connectivity is the simulation graph. Skeleton resources are described externally in Task 007a; no integrated, verified full MaleCNS morphology pipeline or anatomical rendering substrate is established here. Thus a truthful subset soma-point view may be possible after coordinate/provenance validation, but an actual anatomical CNS rendering is **not ready now**. Use graph layouts with explicit “layout is schematic” text; do not place unknown neurons at invented anatomy positions. No new morphology download in A001.

## Application architecture and rendering

| Option | Assessment |
| --- | --- |
| A. Local Python HTTP server + browser | Direct Python engine, lazy optional CuPy, Windows browser support, SSE/WebSocket phase events, Canvas/WebGL graph, clear backend authority, future remote execution; packaging a local launcher remains work |
| B. Python backend + desktop shell | Same engine and renderer, better desktop packaging but extra process/runtime and security surface; possible later wrapper |
| C. Python-native GUI | Direct engine but complex large-graph/timeline rendering and Windows GUI packaging/threading |
| D. Notebook UI | Good research inspection but weak repeatable user flow, process state and distribution |
| E. Static result viewer | Strong offline audit/share path, cannot launch/observe runs alone; useful export companion |

Choose **A**, localhost Python execution service plus browser frontend; no fixed frontend library in A001. Bind loopback only, use an unguessable session token and origin checks for mutating requests, reject arbitrary paths/commands, and provide a local file picker/registered dataset identity through backend validation. No remote service or data upload required. CPU opens without CuPy/GPU; CUDA is opt-in for simulation. Browser authoritative calculations are prohibited. Use Canvas 2D for bounded graph and spike raster initially, SVG for small overlays/labels and controls, Canvas/SVG for timeline/charts; WebGL is a measured escalation for larger subgraphs. Full graph requires aggregation/tiles/WebGL and separate evidence. WebGPU is not first-slice dependency.

## Comparison and robustness

Comparison key binds dataset/graph, side/population, target, duration/dt, frequency, model/sign policy, backend, trial/seed pairing and observable definition; only intervention differs. Baseline/intervention/DELTA show target spike count and firing rate `spikes*1000/duration_ms`, absolute delta `intervention-baseline` and relative delta only if baseline is nonzero (`null` plus `ZERO_BASELINE` otherwise). Multi-trial summaries and paired differences are backend calculations with declared aggregation, not Task 010's frozen effect classification unless independently specified. Temporal response uses authoritative target spike timesteps and declared bins; Task 011 temporal functions are only used when their full input/assumption contract is satisfied. Graph filtering cannot imply causality.

New robustness requests explicitly enumerate R0 and chosen V1–V7 definitions, parameter deltas, seed pairing, trial counts, technical validity gates, and declared aggregation rule ID if any. Backend stores each variant spec identity, target result, warnings and optional defined direction/category. Missing/failed variants remain visible and aggregate status is `INDETERMINATE`; without an explicit backend rule aggregate verdict is `NOT_DEFINED`. Historical Task 017 `NOT_ROBUST` remains visible as historical context, never automatically inherited by a new run. Frontend may display the backend's rule, never calculate a verdict.

No arbitrary shell execution, arbitrary path execution, frontend credentials, automatic upload, or remote simulation dependency. Result paths are service-generated under a controlled result root; file reads/exports resolve against it. Document the localhost trust model and token lifecycle in A002. Preserve historic datasets, Task 017 archive and B: archive as read-only external evidence.
